Four attributes and a script tag

${when}

Template languages start small. Then somebody needs a date formatted.

Liquid has filters. Jinja has filters and macros. Handlebars has helpers. Blade has directives. Each one was added for a reason. The reason repeats: a person was standing in a template, and the template could not do the thing.

${html(s.grown)}

Filtering, sorting, limiting and formatting, all in the markup. Every one of those steps is a decision about the data.

Why a template language grows

The code that made that data is in another file. A view function, a controller, a resolver. To format the date there you open that file, find the function, add a field, and come back to the markup to print it.

The filter is one edit, where you already are. That is why it wins, in every language that offers one.

Then the language has somewhere to put the next thing. Sorting arrives, then pluralizing, then a helper that renders a partial, then a tag that runs a query. The template becomes a second place to write code, in a language with no debugger and no types.

PHP and ERB answer the same pressure from the other end. They put the whole language in the template, and then the work is keeping the query out of the view. That is a matter of discipline, and a template that can run a query will hold one eventually.

The same list here

${html(s.four)}

Four attributes decide what renders: if, else-if with else, each, and key. Then ${empty}, which prints an expression and escapes it. That is the whole language.

An expression reads data and calls functions. There is no assignment, no arrow function, no object literal and no await. A line like ${filterCall} does not parse. There is no filter syntax, and no registry to add a helper to.

Which leaves the question of where the sorting went.

Up, into the same file

${html(s.loader)}

That is the file behind the index of this blog. Sorting is a function call. The date is formatted by another one, four lines above the markup that prints the result. Neither needed a feature in the template language, because neither one was a walk to another file.

A template language grows to fill the distance between the markup and the code. Take the distance away and it stops growing.

One file, two languages, one concern

Server code inside an HTML file reads as mixed concerns. That depends on what a concern is.

HTML, CSS and JavaScript are three languages. They were never three concerns. The test that holds up is what changes together. Add a published date to a post and three things move: the query, the shape it returns, and the markup that prints it.

Split the page by language and every change is two files. Split the app by page and most changes are one.

Carson Gross calls the other half of this locality of behavior: what an element does should be visible where the element is. A server block is the same argument, one level up.

Two costs come with it. An editor reads the script blocks in a page as one module and reports the overlap, so a project turns one setting off. And a page with a long loader is a long file. The answer to the second is the answer anywhere else: the loader imports a module, which is what posts.js is above.

What a small grammar bought

The compiler parses every expression, so it can collect every name a template reads. That walk is short because an expression cannot declare anything.

Collecting those names is where the type checking comes from. The page below has a misspelling in it.

${html(s.typo)} ${html(s.caught)}

Nothing here is annotated. The type of the page's data is whatever the loader's return value infers to, and the markup is checked against it. The two halves are one module to the checker because they are one file. A loader somewhere else would need a declared type to connect them, and somebody would have to keep that type current.

Maintenance looks different too. The compiler refuses ${refused} kinds of mistake and adds no features. if and each on one element is one of the refusals, because Vue 2 and Vue 3 disagreed about which one runs first. Saying no costs an error message. Saying yes costs a feature, its documentation, and its interaction with every feature after it.

The template half of this compiler was the cheap half. The expensive half is the shadow boundary, where markup re-renders in a browser and a key starts to matter. A small grammar did not make that part cheap.

Alone, and then not alone

Alone, what you gain is the walk you do not take. The page is one file, and a question you have while editing markup is answered by scrolling up.

On a team, three things change, and all three are about the diff.

A change to a page is a change to one file. The reviewer reads the data and the markup in the same hunk, and can tell whether post.when exists without opening anything.

A rename is caught, because the loader and the markup are one module to the checker. Renaming a field in one and not the other is a type error rather than an empty string in production.

Two people editing the same page get a merge conflict. That is the cost, and it is the better failure. Two clean merges into a page that disagrees with itself is the other one.

Whether this holds at the size of a large team is the part nobody has evidence for. The three claims above are mechanical, about files and diffs. How forty people feel about them is a separate question, and I have not run that experiment.

The count

Open the template you changed most recently. Count the things in it that are there because the code was somewhere else. A filter, a helper, a partial taking six arguments, a tag that runs a query.

That count is the distance between your markup and your code. It is worth knowing whatever you build with.
