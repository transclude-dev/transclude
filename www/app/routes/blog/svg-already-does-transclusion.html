SVG already does transclusion

${post.date.toDateString()}

Every icon system on the web is built on a feature nobody calls by its name. You write a shape once, give it an id, and point at it from anywhere.

${html(s.sprite)} ${html(s.use)}

Three elements, one definition. Change the path and all three change. The browser does the pointing, and nothing runs to make it happen.

That is transclusion: a document naming a piece of another document, and the piece appearing in place. Ted Nelson coined the word in 1980 for exactly this. The browser has shipped a working version since 2011.

It works for shapes. That is the whole of it.

What the alternative costs

Without <use> you inline the shape at each site.

${html(s.inline)}

Now the definition is copied. Three copies drift, and a fourth appears in a template someone wrote last month. This is the same problem a partial solves on the server, and the same problem a component solves in a client framework.

The interesting part is that the platform solved it once, narrowly, and then stopped.

Why it stopped at shapes

There is no HTML equivalent. There is no tag that says "render the element with this id, from that document, here".

${html(s.img)}

That is not a thing. <img> takes an image. <iframe> takes a whole document and gives it its own box, its own styles and its own scrollbar. That is a different feature wearing similar clothes.

HTML Imports came closest. <link rel="import" href="/header.html"> loaded a document, and Chrome removed it in February 2020.

Even they were not this. An import loaded the file and stopped. The content did not appear anywhere: you reached into link.import and cloned the nodes you wanted. Declarative loading, imperative insertion.

So the gap where a plain declarative include should be has never had anything in it. The one shipped feature that renders a named piece of another document in place is still <use>, and it still only does shapes.

What everyone does instead

Fetch the document, parse it, find the element, put it somewhere.

${html(s.fetchIt)}

That is what htmx does, and Turbo, and every hand-rolled version in between. It works. It also means the piece you swapped in and the page it came from are two renders of the same thing. Nothing checks that they still agree.

A partial template drifts from the page that also renders it. An endpoint returns markup that used to match and now does not. The bug is silent, because both halves are individually correct.

The shape of the missing feature

<use> gets one thing right, and it goes past most people. The definition and the use are the same markup. There is no second copy that can disagree, because there is no second copy.

Everything else about it is a limitation: shapes only, same origin, and a shadow boundary that makes styling awkward. Those are the parts worth leaving behind. The part worth keeping is that one definition serves every use of it.

Put a fragment of a document on a URL, and render it from the same markup that renders the page. That is the version of this HTML never got, and you can build it on a server today. It is what this framework does. The idea is not the framework's, though. It is fifteen years old and already in your icons.
