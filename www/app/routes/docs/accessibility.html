What the default already does

A page ships no JavaScript. The text is on screen before any script runs, so a slow network or a blocked bundle changes nothing about what is readable.

Navigation is links and forms. Back, forward, find in page, open in new tab and reader mode all work, because nothing replaced them.

An element renders into the page's own DOM. There is no boundary between a label and the input it names, so this works.

${html(s.label)} <label for> cannot cross a shadow boundary. An element with export const shadow = true has to carry the label inside its own root. See elements for the rest of what the boundary costs.

What a new project starts with

The layout npm create @transclude writes already carries the parts that are hard to add to a page later.

${html(s.skip)}

The skip link is first in the document, so a keyboard reaches it before the nav. It is offscreen until it takes focus.

${html(s.skipCss)}

position: absolute, not display: none. Nothing hidden the second way can be focused at all, so the link would never appear.

aria-current="page" marks the link you are on. A screen reader announces that one as the current page.

The language of the page

lang in transclude.config.js sets <html lang> for every page. A screen reader picks a voice from it, so a wrong value is worse than a missing one.

${html(s.lang)}

A page that is written in another language sets its own. See languages.

Icons

An icon beside its own label repeats it, so svg-icon hides it. Pass label when the icon is the only thing saying what the control does.

${html(s.icons)}

The two are different elements in the output. A labeled icon is role="img" with an aria-label, and a decorative one is aria-hidden="true". See icons.

Saying something changed

A form submits and the server sends a new page, so a screen reader reads the result the way it reads any document. Nothing has to announce it.

A fragment swap is different. The browser stayed on the page, and only part of it changed. Put the changed text in a live element, and a screen reader reads it out.

${html(s.live)}

role="status" is polite, so it waits for a pause. role="alert" interrupts, so keep it for something that has gone wrong.

A light element writes text and attributes into the nodes already in the page. It never replaces a child, so focus and selection stay where the reader put them. Swapping a whole fragment is your own code, and moving focus after one is yours to do.

Color

The generated stylesheet declares both schemes on :root, and the layout says so in a <meta> that is read before the CSS arrives.

Do not carry meaning in color alone. This site's own warning notes carry an icon as well as a border, because the border is the part some readers cannot use.

What is still yours

The framework renders the markup you wrote. It adds no roles, invents no labels and reorders nothing.

  • Headings in order, one <h1> a page.
  • A name on every control, and on every image that carries meaning.
  • A visible focus style, on everything a keyboard can reach.
  • Contrast that holds in both color schemes.
  • A keyboard path to anything a pointer can do.

The last one is the one a framework cannot help with. A tab list or a menu is a keyboard contract, and writing one is a pattern to follow rather than a component to install.
