Every tool here is good. Some of them are older and better supported than this one. The differences below are real, but none of them is a complaint.

If you want a client application, this page and this framework are not for you. React, Svelte and their frameworks exist because some problems really are applications. This framework is for the much larger set of pages that are not.

Astro

Astro has the goals closest to this framework. Both send HTML, and both prerender what they can. In both, client JavaScript is something that you opt into.

The difference is what happens when part of the page must change. Astro uses an island. An island is a component that hydrates in the browser. So the page must send the runtime of the framework that the component uses.

${html(s.astro)}

An element with behavior is like an island. It is server-rendered markup, and a definition upgrades it in the browser. But the default here is different. A part of the page that changes has its own URL. The server renders it and sends back markup.

${html(s.here)}

Astro is better if you want a large ecosystem, MDX, content collections and image handling. With Astro, you can also add a React component and then stop thinking about it. This framework has none of that.

This is better when the interaction is a form, or a swap of server-rendered markup. You do not have to ship anything for either one.

Enhance

Enhance is the tool most like this one. Read about it before you choose either. It is HTML-first, it uses custom elements and light DOM, and it renders on the server. Progressive enhancement is the default, not a mode.

We agree on most things. Two things are different. First, an Enhance element is a JavaScript function that returns a template string.

${html(s.enhance)}

An element here is an HTML file that the framework compiles.

${html(s.element)}

The second difference is the fragment. In Enhance, you cannot mark an element and get a URL for it. So you write a route for each partial response. One such route is a small job, but the fifth one is not.

Enhance is better if you want an older tool with a company behind it. It also has a complete design system approach, and hosting that knows the framework. It is the safer choice today, and I do not dispute that.

This is better if you want each element to be a file that a designer can open. It is also better if you came for fragments as URLs.

htmx

htmx is not a competitor. htmx swaps HTML into a page, and this framework includes nothing that swaps.

htmx needs a server that returns fragments of HTML. Usually, most of the work is to write those fragments. You need a partial template, a route to serve it, and a second copy of the markup. That copy can drift from the first.

Here, the fragment is the same compiled markup as the page, at its own URL. So htmx and this framework work well together. One of the examples shows this.

Use htmx with the server that you already have. If that server is this one, you write less server code.

Eleventy

Eleventy is a static site generator, and a very good one. It builds files, and it works with many template languages. It needs no server at all.

Both tools prerender pages. The difference is everything after that: forms that post, loaders that run for each request, actions, cookies and sessions.

Eleventy is better for a content site that never needs a server. It has more plugins and more templating choices. To deploy it, you upload only files.

This is better when part of the site must answer a POST. With a generator, you must add a second system for that.

Nue

Nue is standards-first, like this framework. It cares more about CSS and design than this framework does. It keeps content, layout and style separate, and it is strict about that.

Nue is better if the design system is the hard part of your project. It is also better if you want opinions about content structure. Its answers there are more complete than anything here.

This is better if the server half is the hard part. That means routes that load data, forms that write it, and parts of a page that update.

Next, Remix, SvelteKit and the rest

Most people build server-rendered pages with these tools, and the tools do it well. Each one is also a client framework. So the page arrives, and then the browser builds the same UI a second time.

This gives you real benefits: client routing, optimistic updates, and a component model that works in both places. The cost is a runtime download and a second copy of the state.

They are better for an application, such as a dashboard or an editor. They fit any page that is a shell around a long session.

This is better for a document that has some behavior. Most of the web is like that. Why transclude gives the longer version of this argument.
