Every tool here is good, and some of them are older and better supported than this one. The differences below are real, and none of them is a complaint.

If you want a client application, none of this is for you and neither is this framework. React, Svelte and their frameworks exist because some problems really are applications. This is for the far larger set of pages that are not.

Astro

The nearest in spirit. Both send HTML, both prerender what they can, and both treat client JavaScript as something you opt into.

The difference is what happens when a piece of the page has to change. Astro's answer is an island: a component that hydrates in the browser, which means shipping the runtime of whatever framework wrote it.

${html(s.astro)}

An element with behavior is an island by another name: server-rendered markup that a definition upgrades in the browser. The default is different. A piece of the page that changes is a URL, the server renders it, and what comes back is markup.

${html(s.here)}

Astro is better for a large ecosystem, MDX, content collections and image handling. It also lets you drop a React component in and stop thinking about it. This has none of that.

This is better when the interaction is a form, or a swap of server-rendered markup. Nothing has to be shipped to get either.

Enhance

The closest thing to this that exists, and worth reading before you pick either. HTML-first, custom elements, light DOM, server-rendered, progressive enhancement as the default rather than a mode.

We agree on most of it. Two things differ. An Enhance element is a JavaScript function returning a template string.

${html(s.enhance)}

An element here is an HTML file, compiled.

${html(s.element)}

The second difference is the fragment. Enhance has no equivalent of marking an element and getting a URL for it, so a partial response is a route you write. That is a small thing until it is the fifth one.

Enhance is better when you want something older with a company behind it, a worked-out design system story, and hosting that knows the framework. It is the safer choice today and I would not argue otherwise.

This is better if you want the element to be a file a designer can open. Or if fragments as URLs is what you came for.

htmx

Not a competitor. htmx swaps HTML into a page, and this framework ships nothing that swaps.

What htmx needs is a server that returns fragments of HTML. Writing those is usually the work. A partial template, a route to serve it, and a second copy of the markup that can drift from the first.

Here the fragment is the same compiled markup as the page, on a URL. So the two compose well, and one of the examples is exactly that.

Use htmx with whatever server you already have. If that server is this one, you write less of the other half.

Eleventy

A static site generator, and a very good one. It builds files, it is template-language agnostic, and it needs no server at all.

The overlap is prerendering, which both do. The difference is everything after it: forms that post, loaders that run per request, actions, cookies and sessions.

Eleventy is better for a content site that never needs a server. It has more plugins, more templating choices, and a deployment story that is just files.

This is better when part of the site has to answer a POST. Doing that with a generator means adding a second system.

Nue

Standards-first, like this one, and more serious about CSS and design than this one is. It treats content, layout and style as separate concerns and holds that line carefully.

Nue is better if the design system is the hard part of your project, or if you want opinions about content structure. Its answers there are more developed than anything here.

This is better if the server half is the hard part. Routes that load data, forms that write it, pieces of a page that update.

Next, Remix, SvelteKit and the rest

These are how most people build server-rendered pages, and they are good at it. Each one is also a client framework, so the page arrives and then the same UI is built a second time in the browser.

That buys real things: client routing, optimistic updates, and a component model that works in both places. It costs a runtime download and a second copy of the state.

They are better for an application: a dashboard, an editor, anything where the page is a shell around a long session.

This is better for a document that has some behavior, which is what most of the web is. Why transclude is the longer version of that argument.

The short version

If you want Use
A rich client application Next, Remix, SvelteKit
A content site with a big ecosystem Astro
Files only, no server Eleventy
A design system to be the center Nue
HTML-first with a company behind it Enhance
Any element to be a URL, and JavaScript only where you add behavior this
Every project here is worked on, and some of what is written above will go out of date. Check theirs before you decide, not only this page.
