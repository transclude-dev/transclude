What the compiler decides

The file stays valid HTML. Directives are attributes, so a real parser gives a correct tree and Prettier, Emmet and your linter keep working. That is the difference between this and a template language that happens to look like HTML.

Everything is escaped. \${x} always escapes. \${html(x)} is the only way out, and it is a marker object rather than a naming convention, so it cannot happen by accident. Attribute values escape by attribute rules, which are not the same rules.

false, null and undefined drop an attribute rather than becoming a string, so nothing renders class="false". true writes the name bare. An object or an array serializes as JSON. That is what lets the browser read a prop back off the element and render from the same data the server had.

${html(s.drop)}

else binds across whitespace and comments. An else with no if is a compile error with a line number, rather than an element that quietly never appears.

if and each on one element is refused. Vue 2 and Vue 3 disagreed about which runs first, and everyone lost. Wrapping one in a <template> says which you meant.

${html(s.both)}

Conditions are expressions, not strings. if="0" is false. The grammar is small on purpose: no assignment, no arrow functions, no object literals. That keeps a template declarative rather than a second place to write code. It is also what makes it possible to collect the names a template reads, which is where the type checking comes from.

A <template> carrying a directive is consumed. One without any is emitted as it is, so it survives to the browser for content.cloneNode(true).

${html(s.template)}

Comments are stripped from the output, and still count as insignificant when linking an else to its if.

A nested loop name shadows, with a warning. The inner one wins, and the compiler says the outer one became unreachable.

Before 1.0

Below 1.0, a minor version may break something. Every release that does says so at the top of its notes, with the change to make. Two have so far. Both were narrow, and both were the compiler starting to refuse code that was already not doing what it looked like it did.

Settled

These are what the framework is. Changing one would be a different project, not a version.

  • A page is an .html file, and the directory tree is the route table.
  • <script server> holds the loader, and verb exports answer the other methods.
  • fragment gives an element a URL, and the same compiled markup serves it inline and alone.
  • An element in elements/ is light DOM unless it asks not to be.
  • A page ships JavaScript only for an element with behavior, so a page of plain markup ships none.
  • A shadow element renders the same whether the server sent it or the browser made it. export const shadow = true is a boundary, not a second implementation.

Still moving

This works and is documented. It could also change shape before 1.0, so weigh that if you build on it.

  • What the compiler refuses. The list grows when a mistake turns out to be silent, which is what both breaking releases were. Expect it to keep growing.
It was listed as still moving for two reasons. It is the harder half to keep correct. And nobody knew how much of it the tests reached. Now somebody does. A shadow root, setHTMLUnsafe and a template the parser turned into a boundary need a real browser. The checks in the showcase are that. npm run test:coverage reads V8's own numbers back: 98.5% of src/runtime/index.js, over 63 checks.

Measuring it is what found the gap. Every shadow check started from markup the server had sent, so the browser always adopted a root the parser built. An element made with document.createElement takes the other branch, attaches its own root and paints it, and that path had no check at all. It has two now.

The context a loader is handed and the config keys are settled ahead of 1.0. A field or key may still be added. None will be renamed or removed without a major, and tests pin both documented tables to the code.

A patch fixes something. A minor may add a refusal, which is the shape a break takes. A major renames or removes, and nothing else does.

The whole policy is VERSIONING.md in the repository. It says what is covered, what is not, and the test that pins each promise to the code. It is the only copy: a promise kept in two places gets made twice and differently.

What it does not do

Not a roadmap. Each of these is either a decision or a cost that has not been worth paying.

By decision

  • No client-side router and nothing that swaps. Every link is a document request unless you bring something. Fragments give it a URL; htmx, Turbo or a short fetch does the swapping.
  • No session store and no database opinion. Signed cookies are the building block. A store needs a choice this does not make.
  • A page does not stream. Its body is buffered so it can be hashed, which is what buys the strong ETag, and a synchronous render is what lets an include resolve before the page renders. A Link: rel=preload header goes out first, so a proxy can turn it into a 103 while the page is still being made. An endpoint is not a page: it returns a Response you build, so it can answer with a ReadableStream and stay open.
  • Layout loaders run in order, not at once. Each one can read what the ones above it returned.
  • <transclude> does not import an SVG file. It names a piece of a document, and a whole file is not one. Its src is read at compile time, so it cannot be interpolated, and an icon name usually is. Pointing at a shared symbol is also a different claim from the one an include makes, which is that the markup is here. Icons answer that with <use> instead.
  • No element ships with the framework. Elements come from your elements/ directory, and that is the only place they come from. A built-in would make the answer to "where is this element" two answers, and an icon element is the kind of file people edit. So svg-icon.html is scaffolded instead: a new project has it, and it belongs to that project. See icons.

By platform

  • No byte ranges on workerd. A Range request gets 200 rather than 206. Ranges are what a filesystem buys, and a worker has none.
  • A form inside a shadow root is invisible to a document-level listener, because submit does not cross the boundary. Listen on shadow.
  • @scope is soft. A light element's styles lose to page CSS of equal specificity. That is right for content and a hazard for a widget, which is one reason to reach for a shadow root.
  • A light element writes; only a shadow one rebuilds. Both react to a prop change, but a light one does not own its children, so an if or an each over a changing value needs the boundary.

Rough edges

  • The unused-prop check reads <style> and <script> by word, so a prop mentioned in either is assumed used.
  • In dev, Vite logs Failed to load url for a <script head src> pointing at a public file. The file exists and the server sends it. Vite does not own it, and silencing the warning would mean letting Vite serve the public directory, which is the split that keeps dev and production honest.
  • transclude-check is a separate step. The dev server compiles without it, so a type error does not stop a page rendering. It stops the check.
