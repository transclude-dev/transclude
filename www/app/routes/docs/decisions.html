What the compiler decides

The file stays valid HTML. Directives are attributes. So a real parser builds a correct tree, and Prettier, Emmet and your linter keep working. A template language that only looks like HTML cannot do that.

Everything is escaped. \${x} always escapes. \${html(x)} is the only way to skip escaping. It is a marker object, not a naming convention, so you cannot use it by accident. Attribute values escape by attribute rules, which are different.

false, null and undefined drop an attribute instead of becoming a string. So nothing renders class="false". true writes the name with no value. An object or an array serializes as JSON. So the browser can read a prop back from the element and render from the same data the server had.

${html(s.drop)}

else links to its if across whitespace and comments. An else with no if is a compile error with a line number. It does not become an element that silently never appears.

if and each on one element is refused. Vue 2 and Vue 3 ran them in different orders, and that confused people. Wrap one of them in a <template> to say which runs first.

${html(s.both)}

Conditions are expressions, not strings. if="0" is false. The grammar is small on purpose: no assignment, no arrow functions, no object literals. So a template stays declarative, and it does not become a second place to write code. The small grammar also lets the compiler collect the names a template reads. The type checking uses that list.

A <template> with a directive is consumed. One with no directive is output unchanged, so it reaches the browser for content.cloneNode(true).

${html(s.template)}

Comments are stripped from the output. The compiler also skips them when it links an else to its if.

A nested loop name hides the outer one, with a warning. The inner name wins, and the compiler warns that the outer one is now unreachable.

What will not change

These rules define the framework. A change to one would make a different project, not a new version.

  • A page is an .html file, and the directory tree is the route table.
  • <script server> contains the loader, and verb exports answer the other HTTP methods.
  • fragment gives an element a URL. The same compiled markup serves it inline and alone.
  • An element in elements/ uses light DOM unless it asks for a shadow root.
  • A page ships JavaScript only for an element with behavior, so a page of plain markup ships none.
  • A shadow element renders the same way, whether the server sent it or the browser made it. export const shadow = true adds a boundary, not a second implementation.

One thing does keep changing, on purpose: the list of things the compiler refuses. The list grows when a mistake turns out to be silent. A refusal rejects only code that already did not do what it seemed to do. So a longer list is a minor version, not a major one.

A patch fixes bugs. A minor may add a refusal, and that is the only kind of break allowed without a major. Every release that adds a refusal names it at the top of its notes, with the change to make. A major renames or removes things, and the goal is to never need one. The shadow half is the harder half to keep correct. A shadow root, setHTMLUnsafe and a template that the parser turned into a boundary all need a real browser. The checks in the showcase run in one. npm run test:coverage reads back V8's own numbers: 98.5% of src/runtime/index.js, over 63 checks.

The measurement exists to show that both branches are covered. In one branch, the parser builds the root and the browser adopts it. In the other, an element made with document.createElement attaches its own root and paints it.

The context that a loader receives and the config keys were settled before 1.0. A new field or key may still be added. None will be renamed or removed without a major. A test pins each documented table to the code.

A subpath in exports and a name behind it are two separate promises. The paths are settled. The names an app may import are a shorter list, and VERSIONING.md lists them. A subpath like /runtime is for the framework's own use. Its path stays, but the names behind it can change, because the compiler emits calls to them.

A patch fixes something. A minor may add a refusal, which is the one kind of break it allows. A major renames or removes things, and no other release does.

The full policy is VERSIONING.md in the repository. It says what is covered, what is not, and which test pins each promise to the code. It is the only copy, because two copies of a promise soon say different things.

The notes for a release are the message on its tag, on the releases page. There is no changelog file, for the same reason. A release that adds a refusal names it in the first lines, with the change to make.

What it does not do

This is not a roadmap. Each item below is either a decision or a cost that was not worth paying.

By decision

  • No client-side router and nothing that swaps markup. Every link is a document request unless you add a library. Fragments give a part of a page its own URL. htmx, Turbo or a short fetch does the swapping.
  • A type error does not stop a page from rendering. The dev server reports the error and serves the page anyway. transclude-check is the step that fails, and CI runs it.
  • No session store and no database choice. Signed cookies are the building block. A store needs a choice that this framework does not make.
  • A page does not stream. The server buffers its body so it can hash it, and the hash gives the strong ETag. A synchronous render also lets an include resolve before the page renders. A Link: rel=preload header goes out first. It names the stylesheet, the client entry and the chunks it imports. So a proxy can turn it into a 103 while the server still makes the page. An endpoint is not a page. It returns a Response you build, so it can answer with a ReadableStream and stay open.
  • Layout loaders run in order, not at once. Each one can read what the ones above it returned.
  • <transclude> does not import an SVG file. It names a piece of a document, and a whole file is not a piece. The compiler reads its src at compile time, so you cannot interpolate it. But an icon name is usually a variable. Also, an include says that the markup is here, in this page. A reference to a shared symbol says something different. Icons use <use> for that instead.
  • No element ships with the framework. Elements come only from your elements/ directory. A built-in element would give two answers to "where is this element?" Also, people often edit an icon element. So svg-icon.html is scaffolded instead: a new project has it, and it belongs to that project. See icons.

By platform

  • No byte ranges from dist/edge. A file that the edge serves answers a Range request with 200, not 206, because the edge does not answer ranges. A worker that bundles its files answers ranges from memory, as Node does from disk.
  • A document-level listener cannot see a form inside a shadow root, because submit does not cross the boundary. Listen on shadow.
  • @scope is soft. A light element's styles sit in a cascade layer. So any page CSS beats them, whatever its specificity. That is right for content, but it is a risk for a widget. It is one reason to use a shadow root.
  • A light element writes text and attributes; only a shadow element rebuilds. Both react to a prop change. But a light element does not own its children. So an if or an each over a changing value needs the shadow boundary.

Rough edges

  • The unused-prop check matches names by word. It reads the code in <style> and <script element>, and it skips the comments. So a prop that only a comment names is still reported. If a prop's name appears in either block for another reason, the check assumes the prop is used.
