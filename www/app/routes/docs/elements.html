The file name is the tag name. It must contain a dash, because a valid custom element name needs one. A file name with no dash stops the build, and the error names the file.

${html(s.light)} ${html(s.use)}

The style block goes into <head> one time, even when the element appears many times. :scope is the element itself.

Elements that several apps share

elementsDir can list several directories. So the build reads a package of shared elements together with the app's own elements. Each entry is a path from appDir, and a path can go outside it.

${html(s.shared)}

Each tag comes from one file. If two of the directories contain the same tag, the build stops and names both files. It does not silently pick one. The dev server watches every directory, including one outside the project.

Use a light element unless you need a shadow root. A light element costs less, and your CSS applies to it. It renders the same way for a whole page and for one fragment of it. Use a shadow root when the element must keep its styles and DOM separate from the page. Also use one when it must re-render on its own.

What each can re-render

Both kinds react when a prop changes. A light element updates the text and attributes already in the page, so its nodes stay the same nodes. It never replaces its children. The children include the markup the caller put in the slot, and the page's own script can hold references to them.

Only a shadow root lets an element rebuild its structure. In a light element, the build refuses an if or an each over a value that changes. The error names shadow.

An element watches its props only after it is defined. It is defined only when it has behavior, members, or form association. A light element of plain markup still sends nothing to the browser.

What <slot> means in each

In a light element, the server fills the slot and sends the result. No <slot> gets to the browser, because the server placed the markup one time. Fallback content works, and named slots work too. A child with slot="aside" fills <slot name="aside">, the same way the browser does it in a shadow root. A <template slot="aside"> fills it with the template's content. The other children fill the default slot.

In a shadow element, the slot is real. The children stay in the light DOM, and the browser shows them through the slot. So slotchange and assignedNodes() work. Content that you add later also goes into its slot.

A browser builds a declarative shadow root when it parses a document. Tools that swap in HTML do not build one. So a shadow element in a fragment arrives empty and paints itself when it connects. A light element arrives complete.

Pointing a label inside

A shadow root stops a <label for> at the host element. To fix this, export referenceTarget with the id of one element in the template. A reference to the host then goes to that element.

${html(s.target)} ${html(s.targetUse)}

A click on the label focuses the input. A screen reader reads "Name" as the input's name. The same is true for aria-labelledby, aria-describedby and the other attributes that point to an element by id. The server writes the target on the declarative shadow root. An element that arrives in a fragment passes the target to attachShadow.

The target is a literal, the same for every element of the tag. The build stops when no element in the template has that id. It also stops when the id uses \${} or is inside an each. A light element cannot have a target. It has no boundary, so a label already reaches an id inside it. Chrome and Edge follow the target. Safari and Firefox have it behind a flag, and they ignore it. The label is then not connected, the same as with no target.

Giving it behavior

connected runs each time the element connects, and this is the element. It receives an AbortSignal that fires when the element leaves the document. Pass the signal to addEventListener, and the listener is removed for you.

A listener on the element itself needs no signal, because it goes away with the element. A listener on document or window stays after the element is gone. So the build warns when you leave out signal there.

${html(s.behavior)}

A public API

export const prototype puts members on the class. Every element of the tag shares them. The framework uses three of the names. connected({ signal }) runs on every connect, and disconnected() runs on every disconnect, so the two come in pairs. updated() runs after every render.

State

A prop comes from outside the element and is stored in an attribute. State belongs to the element, and nothing outside sets it. export const state declares it. Each element gets its own copy.

${html(s.state)}

Each name becomes a property on the element. Setting one schedules a re-render, the same as an attribute change. updateComplete resolves after the render is written.

${html(s.stateUse)}

The template reads props and state from one namespace. So ${'$'}{n} above does not show which one it is. Declaring the same name in both blocks is a compile error.

The server renders state too. So the first paint shows the default that the block declares.

Styling by state

A boolean state field is also a custom state, so CSS can select it. You do not write an attribute or add a class. The state stays out of the document, but a stylesheet still reacts to it.

${html(s.customState)}

This works for booleans only. A custom state is a name, not a value. So CSS has nothing to select on for a number or a string. The custom state changes when the element renders, not when you assign the field. So it changes in the same frame as the markup it styles.

A state field starts at the default its block declares. So the first paint shows that default either way. Any other value comes from something the reader did. So when a custom state differs, the element has already upgraded. Nothing outside the element can set it. The page's markup cannot, a parent cannot, and a URL cannot. Put anything a caller must pass in export const properties.

Objects and arrays

Write any value that is not a string as JSON in the attribute.

${html(s.json)} The JSON is part of the HTML. The element reads it again on every attribute change. For large data, pass an id and load the rest in the page's loader.

An element a form can submit

Export formAssociated, and the browser treats the element as a form-associated custom element. It does not need a shadow root.

${html(s.form)}

Put it in a form, and it acts like an input. The form submits its value under its name. FormData reads it like any other field.

${html(s.formUse)}

Marking it invalid

this.internals is the ElementInternals object the browser provides. So setValidity works the same way as on an input. :invalid matches, the browser blocks the submit, and it shows its own message.

${html(s.validity)}

Call it each time the value changes. Pass no arguments to clear it. The second argument is the message the browser shows. The third argument is the element the message points at.

The browser focuses the third argument to show its message. A light element takes no focus unless it has a tabindex. Without one, pass a control inside it, such as its button. If you do not, the browser blocks the submit and shows no message. The console says the control is not focusable.

A disabling container

A <fieldset disabled> disables every control inside it. A form-associated element inside it gets the disabled custom state. Style it with :host(:state(disabled)). The state follows the fieldset both ways, so it clears when the fieldset is enabled again.

The framework does not use the disabled attribute for this. If an element has its own disabled attribute, the browser treats it as disabled. The browser then stops telling the element when the fieldset is enabled again. So a control disabled that way would stay disabled.

Write export const shadow = true directly. Do the same for formAssociated. Each one becomes a static field on the class, the same for every element of the tag. So you cannot compute either value.
