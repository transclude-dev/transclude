Stay light unless you need one. A light element is cheaper, and your CSS reaches it. It renders the same way whether the browser asked for a whole page or one fragment of it. Reach for a shadow root when the element has to seal its styles and DOM off from the page, or re-render on its own.

What each can re-render

Both react to a prop change. A light element writes the text and attributes already in the page, so its nodes keep their identity. It never replaces its children: they include the markup the caller slotted in, and the page's own script may be holding references to them.

Rebuilding structure needs the boundary. An if or an each over a value that changes is refused in a light element, and the error names shadow.

An element observes its props only once it is defined, and it is defined only with behavior, members, or form association. A light element of plain markup still ships nothing at all.

What <slot> means in each

In a light element the server fills the slot and sends the result. No <slot> reaches the browser: the markup was placed once. Fallback content works, and so do named slots.

In a shadow element the slot is real. The children stay in the light DOM, and the browser projects them through it. That is what makes slotchange and assignedNodes() mean something, and what lets content added later find its place.

A declarative shadow root is built when a browser parses a document. Nothing that swaps HTML parses one, so a shadow element arrives bare in a fragment and paints itself on connect. A light element arrives whole.

Giving it behavior

connected runs once per connect, and this is the element. It is handed an AbortSignal that fires when the element leaves the document. Pass it to addEventListener and the listener is removed for you.

A listener on the element itself needs nothing, since it goes when the element does. One on document or window outlives it, so leaving out signal there is a build warning.

State

A prop comes from the outside and lives in an attribute. State is the element's own, and nothing outside sets it. export const state declares it, and each element gets its own copy.

${html(s.state)}

Every name becomes a property on the element. Setting one schedules a re-render, the same as changing an attribute does, and updateComplete resolves once it has been written.

${html(s.stateUse)}

The template reads props and state from one namespace, so ${'$'}{n} above does not say which it is. Declaring the same name in both blocks is a compile error.

State renders on the server too, so the first paint carries the default the block declares.

Styling on state

A boolean state field is a custom state, so CSS can select it. There is no attribute to write and no class to add on the way past. State stays out of the document, and a stylesheet still reacts to it.

${html(s.customState)}

Booleans only. A custom state is a name, not a value, so a number or a string has nothing to select on. The state lands with the render rather than with the assignment, so it changes in the same frame as the markup it styles.

A state field starts at the default its block declares, so the first paint is that default either way. Anything else is something the reader did, which means the element has upgraded by the time a custom state differs. Nothing outside can set it: not the page's markup, not a parent, not a URL. Anything a caller needs to say belongs in export const properties.

Objects and arrays

Anything that is not a string is written as JSON in the attribute.

${html(s.json)} The JSON sits in the HTML and is read back on every attribute change. For anything large, pass an id and load the rest in the page's loader.

An element a form can submit

Export formAssociated and the browser treats it as a form-associated custom element. It needs no shadow root.

${html(s.form)}

Drop it into a form and it behaves like an input. Its value is submitted under its name, and FormData reads it like any other field.

${html(s.formUse)}

Saying it is invalid

A field that cannot say it is wrong is not really a field. this.internals is the handle the platform hands out, so setValidity works the way it does on an input. :invalid matches, a submit is blocked, and the browser shows its own message.

${html(s.validity)}

Call it whenever the value changes, and pass no arguments to clear it. The second argument is the message the browser reads out, and the third is the element the message points at.

A disabling container

A <fieldset disabled> disables every control inside it, and a form-associated element gets that as the disabled custom state. Style it with :host(:state(disabled)). The state tracks the container both ways, so a fieldset that re-enables clears it.

Not the disabled attribute. An element with its own disabled attribute is disabled by the browser's own reckoning. The browser then stops telling the element when the fieldset lets go, so a control disabled that way would never come back.

Write export const shadow = true directly, and the same for formAssociated. Each becomes a static field on the class, the same for every element of the tag, so neither can be computed.
