Showcase

examples/showcase is the opposite of a small example: it uses every feature, and it is what the framework is tested against. Fragments, includes, light and shadow elements, endpoints, cookies, a feed and a proxy.

The browser checks live there too, at /check. A real form, a shadow root and a dataset are things no test in Node can model.

TodoMVC

examples/todomvc is TodoMVC with forms and nothing else. Add, edit, toggle, delete, filter and clear, in one .html file, shipping zero bytes of JavaScript.

Read it for the shape of a page that changes things. Every control is a submit button in its own form, carrying a hidden intent, so one POST handler covers seven actions. Editing is a link to ?editing=3, which means it survives a reload. Every change ends in a 303 back to the same URL. Adding a todo twice takes two submissions, not one and a refresh.

The store is a module holding an array, so everyone looking at the running app sees the same todos. That is wrong for a real app and useful for a demo you open in two windows. Swap that one file for a database and nothing above it changes.

Blog

examples/blog is the other half. Nothing on it changes, so every page is written to a file by the build. A sitemap and a feed are written beside them.

Read it for what a parameter route needs before it can be prerendered. posts/[slug].html exports paths(), and each name in that list becomes a file and a sitemap entry. A slug that is not a post sets response.status = 404, and the build refuses to write a file for it.

/sitemap.xml is built from the route table, which already knows every URL. /feed.xml cannot be. A route table holds paths, and a feed needs titles and dates, so the config supplies the items.

Search

examples/search is a fragment doing real work. The results are a fragment, so /?q=form&fragment=results returns the list alone.

With no JavaScript the form submits and the whole page comes back. With it, twenty lines fetch the fragment and swap it in. A test asserts the fragment is a substring of the document, which is what keeps the two from drifting.

The two details worth stealing are in those twenty lines. A counter drops a slow answer that arrives after a newer one, and history.replaceState keeps the URL in step so a reload works.

htmx

examples/htmx does the same job as search with htmx instead of a fetch. It is the only app here that sets fragmentHeader.

htmx puts the id it is about to swap in an HX-Target header. Naming that header in the config means the header alone asks for a fragment, so hx-get="/" with hx-target="#people" carries no ?fragment=. Nothing in the page file mentions htmx.

So every call in that file sets hx-swap="outerHTML". htmx swaps innerHTML by default, which puts the returned <ul id="people"> inside the one already on the page, and again on the next keystroke. The htmz note on fragments is the same trap in its other form. csp: true gives script-src 'self', so a script from anywhere else is refused by the browser with nothing on the page to explain it. htmx is copied out of node_modules into app/public/ before the build.

Includes

examples/includes is the feature this framework is named after, from all three sources: the same page, another route, and another site through the proxy.

It is worth reading for one asymmetry. A same-page include drops the id from its copy, because that is always a second copy in one document. A cross-route include keeps it, because that content came from another document and there is one of it here.

Auth

examples/auth is a signed-cookie session and one layout that guards everything below it. The guard returns a Response, so nothing under it runs. Not the layout's own markup, and not the page's loader. Pages in admin/ check nothing, and forgetting to check is not something you can do.

Signing is what makes the cookie a session. The browser can read the id and cannot invent one: send session=1 by hand and the guard turns you away.

That layout reads the session to decide what the header says. So every page under it has an answer per visitor, and none can be a file. The build names the page, exits non-zero and writes nothing, rather than shipping a signed-out copy of your home page. Read the cookie in a narrower layout and only that section pays.

Live

examples/live pushes updates over server-sent events. An endpoint answers with a stream and never closes it, so an endpoint is not only for JSON.

What the stream carries is a nudge, not markup. The list already has a URL, so the client hears one line and asks for /?fragment=feed. Sending rendered HTML down the stream would be a second way to render the same thing.

The socket closing fires abort on request.signal. The consumer letting go of the reader runs the stream's own cancel(). Handle one and not the other and you either leak a listener holding a dead connection, or close a controller that is already closed. Both happened while this was written.

Reading one

Each is an ordinary project. It has its own transclude.config.js, its own package.json and its own tests, and it depends on @transclude/core the way yours does. Copy a directory out of the repository, change the dependency to a version number, and it runs.

Nothing is shared between them, so a file you are reading is the whole answer. Every one is built and tested on each commit, so what is written here is what runs.

Recipes are the short version: one answer at a time, to drop into a project you already have.
