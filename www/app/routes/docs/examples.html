Showcase

examples/showcase is the opposite of a small example. It uses every feature, and the framework is tested against it. It has fragments, includes, light and shadow elements, endpoints, cookies, a feed and a proxy.

The browser checks are there too, at /check. No test in Node can model a real form, a shadow root or a dataset.

TodoMVC

examples/todomvc is TodoMVC built only with forms. You can add, edit, toggle, delete, filter and clear. It is one .html file, and it ships zero bytes of JavaScript.

Read it to see how a page that changes data is built. Every control is a submit button in its own form, with a hidden intent. So one POST handler covers seven actions. Editing is a link to ?editing=3, so a reload keeps you in edit mode. Every change ends in a 303 back to the same URL. So a refresh never adds a todo twice. Only a second submission does.

The store is a module that contains an array. So everyone who opens the live app sees the same todos. That is wrong for a real app, but useful for a demo you open in two windows. Replace that one file with a database, and no other code changes.

Lite-Brite

examples/lite-brite is a Lite-Brite board sized to fit the screen, so you do not scroll. Pick a color, tap a hole, and a peg lights up. It has 240 holes, ten colors and one page.

Read it to see where the drawing is stored. Each hole is a group of eleven radio buttons, so the browser stores the color in it. The server does not know what anyone drew. Eleven labels sit on top of each other over every hole. The color tray decides which label gets the tap. .brite:has(#ink-blue:checked) .hole > label.blue gets pointer-events: auto, and the other ten stay inert. To draw the pegs, CSS reads the same radios back, with one rule per color.

To empty the board, you use <input type="reset">. It returns all 2,651 radios to the value in their markup. The browser already has a button for that.

The 240 holes are 240 copies of the same 23 tags. So 383 KB of markup compresses to 11 KB with brotli. A bigger board costs parse time, not download time. To change the board size, edit the two numbers at the top of the page.

Dungeon

examples/dungeon is a game with fifteen rooms. It has no client JavaScript and no session on the server. The path is the room, and the query string is everything else: /dungeon/vault?have=brass-key,lantern&seen=gate,hall,vault&seed=7f3a.

Read it to see what that gives you. Back is undo, and a bookmark is a save slot. A link sends your game to somebody else's browser. Two players with the same items have the same URL, character for character. Every list is sorted and deduplicated before it goes into the URL. Details that vary come from the seed in the links. So a second visit to a room reads like the first.

A locked door is never a link. An open exit is an <a>, and a locked one is text. So the server never has to refuse a request or explain a dead end. The lock reads have, not a history. A URL with have=brass-key opens the iron door, even if nobody went to the vault for the key. That is the trade: the URL is the save file. So a hand-edited save is a cheat, not an error.

Every room is dungeon/[room].html with export const prerender = false. The static handler looks only at the path. A file written at build time would give every game the state the build had, which is no state.

Elements

examples/elements puts a light element and a shadow element on the same page. So you can see the difference, not only read about it. See elements for the reference.

The page has three elements. The first is light with no behavior, so it registers nothing in the browser. The second is light and interactive. It writes a new number into the text node it rendered. The third has a boundary, and it rebuilds a list from a prop. A light element cannot rebuild like that.

The stylesheet has a rule for each element. The rule for the light element applies. The rule for the inside of the shadow element does not. Nothing in Node models a boundary, so only a browser shows this.

Blog

examples/blog is the opposite case. Its pages never change, so the build writes every page to a file. It also writes a sitemap and a feed.

Read it to see what a parameter route needs before the build can prerender it. posts/[slug].html exports paths(). Each name in that list becomes a file and a sitemap entry. A slug that is not a post sets response.status = 404, and the build refuses to write a file for it.

It also turns precache on, so the build writes /precache.json. A service worker caches the files in that list. This app is the clearest place to see that file.

The build makes /sitemap.xml from the route table, which already knows every URL. It cannot make /feed.xml that way. A route table contains paths, but a feed needs titles and dates. So the config supplies the feed items.

Markdown

examples/markdown is a .md file that is a page. It answers a URL. It starts with the same <script server> block that an HTML page starts with. The server renders the element in it.

Read it for the four lines in app/lib/markdown.js. A page is a template in any format. So \${title} in a paragraph reads from the loader. In a code fence it should not, because a shell sample often contains \${HOME}. Those four lines escape \${ in code and leave prose unchanged.

markdown in the config is a function that turns source into HTML. This package ships no parser. So you choose the flavor, the extensions and the highlighter, in one file.

Search

examples/search uses a fragment for real work. The results are a fragment, so /?q=form&fragment=results returns only the list.

Without JavaScript, the form submits and the server sends the whole page. With JavaScript, twenty lines fetch the fragment and swap it in. A test checks that the fragment is an exact part of the full page. So the two cannot become different.

Those twenty lines contain two details worth copying. A counter drops a slow response that arrives after a newer one. And history.replaceState keeps the URL up to date, so a reload works.

htmx

examples/htmx does the same job as search with htmx instead of a fetch. It is the only app here that sets fragmentHeader.

htmx puts the id of its swap target in an HX-Target header. The config names that header, so the header alone asks for a fragment. So hx-get="/" with hx-target="#people" needs no ?fragment=. Nothing in the page file mentions htmx.

So every call in that file sets hx-swap="outerHTML". By default, htmx swaps innerHTML. That puts the returned <ul id="people"> inside the one already on the page. The next keystroke nests it again. The htmz note on fragments shows the same problem in another form. csp: true gives script-src 'self'. So the browser blocks a script from any other origin, and the page shows no error. Before the build, a step copies htmx from node_modules into app/public/.

Includes

examples/includes shows the feature this framework is named after. It includes markup from all three sources: the same page, another route, and another site through the proxy.

Read it for one difference. A same-page include removes the id from its copy, because the copy is always a second copy in the same document. A cross-route include keeps the id. Its content came from another document, so this page has only one copy.

Auth

examples/auth has a signed-cookie session and one layout that guards every page below it. The guard returns a Response, so nothing under it runs. The layout's own markup does not run, and the page's loader does not run. Pages in admin/ do no checks, so you cannot forget a check.

The signature makes the cookie a session. The browser can read the id, but it cannot invent one. If you send session=1 by hand, the guard turns you away.

That layout reads the session to decide what the header shows. So every page under it is different for each visitor, and no page can be a file. The build names the page, exits non-zero and writes nothing. It does not ship a signed-out copy of your home page. Read the cookie in a narrower layout, and only that section is affected.

Live

examples/live pushes updates over server-sent events. An endpoint answers with a stream and never closes it. So an endpoint is not only for JSON.

The stream sends a signal, not markup. The list already has a URL. So the client gets one line and then asks for /?fragment=feed. If the stream sent rendered HTML, that would be a second way to render the same thing.

When the socket closes, abort fires on request.signal. When the consumer releases the reader, the stream's own cancel() runs. You must handle both. If you handle only one, you leak a listener that holds a dead connection. Or you close a controller that is already closed.

Running them

${html(s.run)}

Each example has its own port, so they can all run at the same time. 1960 is free on purpose. It is the port that a new project gets. An example on that port would collide with the first project you make.

Reading one

Each example is an ordinary project. It has its own transclude.config.js, its own package.json and its own tests. It depends on @transclude/core the same way your project does. Copy a directory out of the repository, change the dependency to a version number, and it runs.

The examples share no code, so each file you read is complete. Every example is built and tested on each commit. So the code you read is the code that runs.

Recipes are the short version. Each one answers one question, and you can add it to a project you already have.
