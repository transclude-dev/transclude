The file

app/routes/notes.html answers /notes. It holds the markup and the code that loads its data.

What it compiles to

One module, with a fixed set of exports. Every later stage reads one of them. This is the real output for the file above, compiled while this page was built.

${html(module)}
Export Came from
load The <script server> default export.
POST The verb export, passed through as it was written.

regions One entry per element marked fragment.
renderTitle, hasTitle The <title>, lifted out of the body.
css The <style> blocks, collected once.

The fragment is the same markup

regions.list is emitted from the <ul>, on the same walk that emitted render. Nine lines of it appear in both, character for character.

${html(regions)} Fragments covers the URL. GET /notes?fragment=list calls this function instead of render, with the data the same loader returned.

What the build decides

The build runs each loader once. A page that reads nothing about the request is rendered to a file. A page that reads a cookie, sets a header or answers with a Response cannot be one file for every visitor. The build names that page, says which of those it did, and exits non-zero.

The production build has the rest.

What answers a request

Everything above the route table runs for every request, including one that ends at a file. The order is fixed.

Step What it does
1 Trailing slash /notes/ redirects to /notes with a 301.
2 CSRF A form post from another origin is refused with a 403.
3 nosniff On every response, a public file included.
4 Your middleware app/server.js, before anything that serves bytes.
5 Public files A real file beats a [...path] catch-all.
6 The route The directory tree, matched.

Inside the route, in this order:

  1. The layout chain, outermost first. Any one can return a Response and stop everything below it.
  2. The action, for a non-GET. The fragment name is checked before this.
  3. The page loader.
  4. render for a document, regions[name] for a fragment.
  5. Includes, the head, and the policy built from what the page inlined.

The same module, four ways

Request What runs
GET /notes load, then render. The whole document.
GET /notes?fragment=list load, then regions.list. The <ul> and nothing else.
POST /notes POST, then the loader and render again.
<transclude src="/notes#list"> load, then regions.list, inside another page. See includes.
The loader runs again after the action, so the page renders from what the action just did. That is two loader runs on a request that changes something, and it is on purpose.

What reaches the browser

The client export above is empty, so this page ships no JavaScript. A page ships some when it renders an element with behavior, and only for those elements. The <script server> block is compiled into the route and never appears in the page.

The explorer is this page with the code in it. Every stage opens the module that does the work, and the whole of src/ is there to read. It runs JavaScript to do that, which is why it is a file beside the docs rather than a page in them.
