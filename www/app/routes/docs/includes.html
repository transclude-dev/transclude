A fragment of this page

The fragment is already a function of the page's data. So to include it, the server calls that function. The markup is in one place, and it renders in two places.

${html(s.same)} ${html(s.sameOut)}

The copy does not get the id. Two elements cannot have the same id. Also, #pricing must point to the fragment that a swap replaces.

A fragment of another route

${html(s.route)}

That route's loaders run, but its layouts' markup does not. The same thing happens when a client asks for a fragment over HTTP. The server renders the fragment in the same process. It does not fetch it. If you include one route twice, its loaders run once, even from inside another include. That one load serves every fragment, so its loader reads ctx.fragment as null. The path is matched the same way as a request, so /notes/ finds /notes.

This copy keeps its id. The fragment is on the other route, so no element on this page has that id yet. If you include the same fragment twice, the page has it twice.

If a page includes a route that reads a cookie, the page is personal too. The cache does not store it, and the build does not write it to a file.

A document that another person wrote

${html(s.site)}

This is the only form that sends a request out of the server. It is also the only form that needs configuration. A page that you did not write marks no fragments. So the server finds the part to take from the page's HTML. The second half of this page explains how. An empty allow is the same as no proxy.

Children are the fallback

If the include works, the children are removed. If the source cannot be read, the children render in its place. If there are no children, a failed source stops the render.

The fallback is for a source that is down. A mistake throws an error instead. Three things count as mistakes: a source that is not allowed, a fragment the other route does not have, and an include that loops.

Resolved before the page renders

The compiler collects the list of includes in a page. The server gets all of them before it renders the page.

So a page can still be a file. A prerendered page reads its sources once, at build time, and keeps the result in the file.

What is refused

${html(s.refused)}

All three are compile errors. A page can also include itself through two other pages. The server catches this when it renders, and the error shows the path of the loop. It also catches a chain more than ten levels deep. A loop can also come back through a different fragment of a route. For example, /y#a includes /z#c, which includes /y#d. The server catches that too.

An include can name a fragment that another route does not have, like /notes#nope. The server refuses it when it renders. A route's fragments are fixed when it compiles, so the name must be a typo.

Reading a document with no marked fragments

Your own pages mark their fragments. A page that another person wrote does not. The rest of this page explains how the server finds a part of that page and makes it safe to show.

An include makes a copy. Your server reads the document and serves the part from your origin, as part of your page. A prerendered page keeps the part in a file that ships with your build. Name a host only when you have the right to republish its content. Read its license and its terms first. A share-alike license can put conditions on the page that contains the fragment.

The framework adds no credit for you. Write the credit yourself, next to the include.

${html(s.credit)}

The license decides what that line must say. A document does not give its author or its license in a form that a program can read. So you must write the credit.

Turning it on

There is no route until you name a host. Every host is denied by default, and the allow list is what protects you.

${html(s.config)}

How the server finds where a part ends

An id names an element, but it does not say where the part ends. The server uses only the structure that HTML already has:

  • A heading takes everything after it, up to the next heading of the same rank or higher. An h2 includes its h3s. An h3 stops at the next h3 or any h2. A run never goes outside its parent element.
  • A <dt> takes its definitions up to the next term.
  • Any other element is returned on its own. The server guesses nothing more.

An empty inline element is a bookmark for the element after it. Older documents write anchors this way. In this example, the id resolves to the heading and its section.

${html(s.bookmark)}

The server follows only one step. An element that contains text or an image is content, not a bookmark.

Documents with no ids

A heading with no id gets one from its text. The text is lowercased, punctuation is removed, and spaces become hyphens. Letters stay in their own script. They do not change to ASCII.

Explicit ids win. The server makes the full table of names before it resolves anything. So a name means the same thing on every request. An id lower on the page wins over a heading higher up. The heading then gets the next name.

A heading run is several sibling nodes, not one element. It arrives in the same order as in the source, so it matches its original page.

What is removed and what is kept

The server removes scripts, frames, plugins and event handlers. It removes javascript: URLs everywhere. It keeps a data: URL only on an image source. It also removes <base>, <link> and <style>, because their effect does not stop at the fragment. A <base> changes every relative URL in the page that gets the fragment. The other two change the styles of that whole page. A <link> loads a stylesheet from any location, and a <style> contains one.

The server also removes SVG animation. <animate> and <set> write an attribute after the cleaning reads it. So they can give an <a> a javascript: URL that nothing checked. A tab or a control character inside the scheme is another way. A browser treats href="java&#9;script:…" as a working URL. So the check reads the scheme the same way a browser does, before it decides.

The server removes comments and the deprecated raw-text elements: <xmp>, <plaintext>, <listing>, <noembed> and <noframes>. A parser reads the content of these elements as text. So the cleaning never sees it. A browser that reads it as markup would run any code hidden there.

The server cleans the inside of a <template>, like any other element. Template content is inert on its own. A declarative shadow root is not inert. shadowrootmode makes it a real shadow tree in your page. A script in it would run on your origin.

The server keeps a style attribute, because it styles only its own element. A highlighted code block gets its colors that way. Set styles: 'strip' to remove them and use your own CSS.

The server makes every relative URL absolute against the source URL. This includes an href that is only a hash. Without this change, it would point to an id in your page. The server parses srcset, because a candidate URL can contain a comma. It also rewrites url() inside a style attribute.

A custom element from the source arrives with no definition. It is inert, so a section made of custom elements looks empty.

A <form> keeps its action, made absolute against the source. If a visitor fills it in on your page, the form posts to the source's host, not yours. The allowlist controls what the server can read. It does not control where the markup points. If a fragment contains a form that you do not want, ask for a smaller fragment.

Limits

${html(s.tuning)}

An unknown key throws an error. The error names that key and lists every valid key. The config does the same for its own keys.

The server follows redirects one at a time, and it checks every step again. A check on your configured URL tells nothing about the target of the third redirect. The server refuses addresses in the private ranges. This includes the cloud metadata endpoint and IPv4 addresses written in IPv6 form.

maxAge is how long the server uses a document it already read, without asking the source again. So several fragments of one page cost one read. After that time, the server revalidates the document with ETag and Last-Modified.

On Node, Bun and Deno, the server resolves a hostname and checks every address that comes back. This covers all four ways to write an IPv4 address inside an IPv6 address. workerd has no resolver, so the check does not run there. On workerd, the allowlist is the only defense.

Where the check runs, the resolver gets the same question twice. The check asks once, and the connection asks again. A DNS record with a short lifetime can expire between the two and return a different address. Nothing before the socket can prevent this. So the allowlist is the real protection. Name only hosts that you trust. A wildcard means that you trust every host under it.

The endpoint

When you name a host, the server also mounts /_transclude/proxy. You can ask it for a fragment of an allowed document from anywhere.

${html(s.request)}

With no id, the endpoint returns the document's outline and a list of what the cleaning removed.

${html(s.outline)}

The endpoint returns the fragment, sanitized and rewritten. It is on your own origin, as the default policy requires. That policy names 'self' and refuses a cross-origin fetch.
