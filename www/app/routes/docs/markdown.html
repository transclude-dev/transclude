app/routes/notes.md answers /notes, the same way notes.html would. Put one of each in a directory and the build refuses, because both claim the URL.

The parser is yours

This package ships no Markdown parser. markdown in the config is a function from source to HTML, the way cache is a store you supply.

${html(s.config)}

Which flavor, which extensions and which highlighter are one file in your app. A .md page with no converter is an error naming the file, rather than a guess about what you meant.

The loader is the same block

A Markdown page opens with the <script server> an HTML page opens with. CommonMark starts an HTML block at <script and ends it at the closing tag. Everything between passes through raw, so the loader reaches the compiler untouched.

${html(s.page)}

There is no frontmatter and no YAML. Interpolation, directives, fragments and type checking all work, because by the time anything compiles there is no Markdown left.

Not even in a comment. The HTML parser ends a script at the first one it sees, and Markdown ends the block there too. The rest of your loader then renders as prose, and the page still builds.

Elements need blank lines

An HTML block runs to the next blank line, and Markdown inside one is not parsed. That is the one rule to carry around.

${html(s.blocks)}

Inline is easier. A tag inside a paragraph needs no blank lines, and the Markdown between the tags is still parsed.

Code fences and \${

A page is a template whichever format it was written in, so \${title} in a paragraph reads the loader. In a code fence that is almost never wanted. A shell sample is full of \${HOME}, and a JavaScript one is full of template literals.

\\${ is the escape and works anywhere in any page. Writing it by hand in every sample is not the answer. Escape the code tokens in your converter instead, which is four lines and leaves prose alone.

${html(s.escape)} It is a judgment about how people write, not a rule about how pages compile. An app that wants a sample to interpolate deletes those four lines.

A diagnostic points into the converted HTML

npm run check checks Markdown pages, and says where the position came from when it reports one.

${html(s.diagnostic)}

The line is real and it is not a line in the file you opened. Getting one back to the Markdown needs a source map from the conversion, and the conversion is yours.

Markdown that is not a page

A directory of Markdown read by one route is data, and it needs none of this. A loader reads the files and hands back the converted body. scanRoutes skips any name starting with an underscore, directories included. So routes/blog/_posts/ sits beside the page that reads it and answers no URL of its own.
