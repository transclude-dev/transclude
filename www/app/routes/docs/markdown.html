app/routes/notes.md answers /notes, the same as notes.html would. If a directory contains both files, the build refuses, because both want the same URL.

You choose the parser

This package includes no Markdown parser. markdown in the config is a function that turns source into HTML. It is like cache, which is a store you supply.

${html(s.config)}

You choose the flavor, the extensions and the highlighter in one file in your app. A .md page with no converter causes an error that names the file. The framework does not guess what you meant.

The loader is the same block

A Markdown page starts with the same <script server> block as an HTML page. CommonMark starts an HTML block at <script and ends it at the closing tag. Markdown does not change the content between them. So the loader gets to the compiler unchanged.

${html(s.page)}

There is no frontmatter and no YAML. Interpolation, directives, fragments and type checking all work. They work because no Markdown is left when the compiler runs.

This includes comments. The HTML parser ends a script at the first closing tag it finds. Markdown ends the block there too. The rest of your loader then shows as text on the page, and the build does not stop.

Elements need blank lines

An HTML block continues to the next blank line. Markdown inside an HTML block is not parsed. This is the one rule to remember.

${html(s.blocks)}

Inline tags have no such rule. A tag inside a paragraph needs no blank lines, and the Markdown between the tags is still parsed.

Code fences and \${

A page is a template in either format. So \${title} in a paragraph reads a value from the loader. In a code fence, you almost never want this. A shell sample is full of \${HOME}, and a JavaScript sample is full of template literals.

\\${ is the escape, and it works anywhere in any page. But do not write it by hand in every sample. Escape the code tokens in your converter instead. That takes four lines, and it does not change the prose.

${html(s.escape)} It is a choice about how people write, not a rule about how pages compile. If an app wants a sample to interpolate, it deletes those four lines.

A diagnostic points into the converted HTML

npm run check checks Markdown pages. When it reports a position, it also says where the position came from.

${html(s.diagnostic)}

The line number is correct, but it is a line in the converted HTML, not in the file you opened. To map it back to the Markdown, you need a source map from the conversion. The conversion is your code.

Markdown that is not a page

A directory of Markdown that one route reads is data, and it needs none of this. A loader reads the files and returns the converted body. scanRoutes skips any name that starts with an underscore, including directories. So routes/blog/_posts/ can sit next to the page that reads it, and it has no URL of its own.

examples/markdown shows all of the above in a running app.
