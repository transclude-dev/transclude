Ethical Web Principles is a W3C Statement from December 2024. It describes what web technology should do for the people using it.

Most of the choices below were made for other reasons. The framework sends HTML and ships no script because that is how a page should work. That choice also meets four of the twelve principles.

The principle What this framework does
There is one web A page is HTML at a URL. Nothing here reads a country, and the build writes one set of files for everybody.
The web does not cause harm to society No telemetry, no analytics and no install script. This package reports nothing anywhere.
The web supports healthy community and debate The repository has a code of conduct, a contributing guide and a security policy.
The web is for all people A page sends no script bundle, so a slow network and an old phone still get the text. See accessibility and languages.
The web is secure and respects people's privacy The content security policy uses hashes of the code that a page inlines. Cookies are HttpOnly and SameSite=Lax. The server refuses to fetch a private address. See security.
The web enables freedom of expression The build writes a directory that any static host can serve. No account and no service stands between you and your readers.
The web makes it possible to verify information Nothing minifies the HTML. When a reader uses view source, they see the page you wrote.
The web enhances individuals' control and power MIT license, five dependencies, four runtimes. No company has to stay in business for it to keep working.
The web is an environmentally sustainable platform A page gets no client entry unless it asks for one. Prefetching is off unless you turn it on. A test checks the count.
The web is transparent This site serves its own source. The refusals page comes from the compiler, not from a list written by hand.
The web is multi-browser, multi-OS, and multi-device Five features need a browser from a known year. Everything else is plain markup. See browsers and runtimes.
The web can be consumed in any way that people choose An element renders into the page's own DOM. So a user stylesheet, an extension and reader mode can all reach it.

Why the last principle holds

A shadow root hides content from a user stylesheet, from some extensions and from some reader modes. In this framework, the page's own DOM is the default, and a shadow root is opt-in.

Navigation is the other half. There is no client router. So back, forward, find in page and open in new tab all work, because nothing replaced them.

Where this falls short

An element with styles needs a 2026 browser. The framework scopes those styles with @scope. Browsers agreed on it in March 2026. A browser without it drops the style block, and the element renders with no styles. The browsers page says what to do about that.

Two headers are off by default. csp and permissionsPolicy each take something away from an app that may need it. So you decide whether to set them. A generated project turns both on, so you can see the settings there.

There is no message catalog. Routing and Intl are enough for a multilingual site. This package ships no catalog format and no fallback chain. Languages says why.

You write a widget's keyboard behavior. The framework renders the markup you wrote and adds no roles. A tab list or a menu must respond to keys in a fixed way. Nothing here writes that code for you.
