Prerendering

The build renders every page to a file. If a page must run on each request, add this line to it:

${html(s.prerender)}

A page needs it if it reads the URL, is behind a guard, or shows data that changes.

The build writes a page with parameters once for each set that its paths() export names. Each param is encoded in the URL, so a b becomes /p/a%20b. The file is written at the decoded path. A param that contains a / stops the build, unless the route is a rest param like [...path].html. An empty param, . or .. also stops the build.

A page that reads a cookie cannot be one file for everyone. The same is true of a page that answers with a Response or sets a status other than 200. The build names the page, says which of those it did, and exits non-zero. It does not write a file that would be wrong for every visitor after the first.

A page that exports an action also stops the build. An action exists to change what the page shows. A file keeps what the page showed at build time. A fragment of the page renders live. If the action changes nothing that the page shows, say so with export const prerender = true. A contact form that sends a message and redirects is an example.

The build also fails if a loader or a template throws during the build. The report names the page, the error, and the line in your .html file where the error came from.

Speculation

Every link is a document request, so every navigation costs a round trip. With speculate: true, the browser can make that trip early:

${html(s.speculate)}

Each page then contains a <script type="speculationrules"> block. No code from this framework runs to make it work. A browser that does not support it ignores it.

What the browser may run, and what it may only fetch

A prerender runs the page. A page that the build wrote to a file has no loader left to run, so running it early costs nothing. These pages go in prerender.

Every route that the server still renders goes in prefetch. Its loader may read a cookie, count a view or give out a token. If the reader only hovers over a link, running that loader is wrong, not only slow. Endpoints are in neither list.

${html(s.speculateOut)}

The build makes this decision, because only the build knows which routes became files.

Options

${html(s.speculateOpts)}

eagerness is moderate by default, so the browser waits for a hover. immediate and eager act before the reader does anything. exclude is matched against the emitted pattern. So to exclude the route /docs/:path{.+}, write /docs/*.

Speculation is a hint, and the browser may ignore it. But when the browser acts on it, the page really runs. If a loader does something that a reader would notice, put prerender = false on that page. That keeps the page out of the prerender list. A pattern in the block looks like a URL, so Googlebot requests it. The route /people/:name is emitted as /people/*. So /people/* comes in as a request. It matches the route, names nobody, and gets a 404. Search Console lists it as a page not found, with no links to it. The 404 is the correct answer. If you do not want the pattern in the block, use exclude.

Holding a render

A third choice sits between a file written once and a render on every request. The server keeps the rendered page for a set time.

${html(s.revalidate)}

Inside that time, the server answers a request from the store, and the loader does not run. After that time, the server sends the stored page immediately. It renders a fresh one behind the response, so nobody waits for a re-render. Only one render runs at a time for each URL, however many requests arrive together.

The key is the path and the query, because a page that reads ?q= renders differently for each value.

The server keeps that rebuild alive with ctx.after. On workerd, that is waitUntil. A worker may stop as soon as it sends a response. Any work that nothing keeps alive stops with it. Node, Bun and Deno keep running either way.

If a rebuild throws, the stored page stays in place, so one bad render does not empty the store. The error goes to onError with the request that started it.

Tags

Seconds say when a page may be out of date. A tag says when it is out of date. So the code that changed the data can drop the page instead of waiting.

${html(s.tagged)}

ctx.revalidateTag drops every stored page with that tag. It is on the context of a page action or an endpoint. So the code that wrote the change also reports the change. If the loader of a prerendered page calls it, the build stops, because the build has nothing stored to drop yet.

${html(s.drop)} The server never keeps a page that read a cookie, set a header, answered with a Response, or has a status outside 2xx. A shared cache that kept one of these would give one visitor's page, or one visitor's Set-Cookie, to the next visitor. The build uses the same rule to decide if a route can be a file. The cache sees only two things: a cookie read and a header written. It does not see a loader that reads Authorization or Accept-Language directly from ctx.request. Such a page must not set revalidate, or it must put what it read in the URL. Also set metadataBase. Without it, an absolute URL is built from the request's own host. A stored page would then contain the host that its first visitor sent.

The default store is a bounded map in the process. That works for one server but not for several. Each server keeps its own copy, and revalidateTag reaches only one of them. To put the store in a place they all share, give cache in the config any object with the same four methods. Each method may return a promise, as a store across a network does. revalidateTag then returns that promise, so await it before you answer.

A list of what to cache

Turn on precache, and the build writes /precache.json. It lists everything the build produced, with a value that tells a cache when each item changed.

${html(s.precacheOn)} ${html(s.precacheOut)}

A prerendered page and a public file keep the same URL between builds, but their bytes change. So each one has its ETag. A hashed asset has revision: null, because its name is its version and its bytes never change.

version changes when any entry changes. Name a cache after it. Then the previous cache is the one to drop, and you do not need to compare lists.

This framework ships no service worker. The build lists what it produced, and other code decides what to do with it. Fragments follow the same rule.

Workbox reads this format directly. So does a service worker that you write. For a site that only needs to work offline, that is about thirty lines.

${html(s.worker)}

It goes in app/public/, so the server serves it from the root and its scope is the whole site. Register it from a page or a layout.

${html(s.register)} /precache.json names hashed asset file names, and only the build knows them. npm run dev answers it with a 404 on purpose. A service worker that caches anything while you edit is a bug. So register it behind a check for production.

Caching

The build compresses its output once, and each encoding gets its own ETag.

What Cache-Control
Hashed assets public, max-age=31536000, immutable
Prerendered pages public, max-age=0, must-revalidate
Server-rendered pages The same, and private, no-cache if the render reads a cookie or sets a header
The 500 page no-store, and no ETag

Public files

app/public/ is copied to dist/public. The server serves it with byte ranges, so media works.

The Content-Type comes from the file extension. The build, both servers and workerd all read it from one table. The table covers what a site serves: audio, video, captions, fonts, images and documents. A file of an unknown kind is sent as application/octet-stream, and the build prints which kinds those were.

Every response has X-Content-Type-Options: nosniff, so a browser must not guess a different type. Say an <audio> element gets application/octet-stream. It may not look in the bytes to find the AAC. The clip does not play badly. It does not play at all.

Error pages

404.html and 500.html are rendered at build time and served as static files. A page that renders after a request has failed can fail too. So these two are always static files.

The build always writes them, so nothing they render may depend on a request. If a layout above them reads a cookie, the build stops. ctx.request is null during prerendering, and only then. A shared layout can use that to skip the part that needs a visitor.

In production, the server logs the error and keeps it out of the page. In dev, you see the stack instead.

A page loads a script only if something on it needs one. A page of plain markup and light elements ships no script.
