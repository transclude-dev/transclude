Prerendering

Every page is rendered to a file at build time. Add this to a page that has to run for each request instead:

${html(s.prerender)}

A page needs it if it reads the URL, sits behind a guard, or shows data that changes.

A page that reads a cookie, answers with a Response, or sets a status other than 200 cannot be one file for everyone. The build names it, says which of those it did, and exits non-zero. It does not write a file that would be wrong for every visitor after the first.

Holding a render

Between a file written once and a render on every request, there is a page held for a while.

${html(s.revalidate)}

Inside that window a request is answered from the store and the loader does not run. Past it, the page already held goes out immediately and a fresh one is rendered behind the response, so nobody waits for a re-render. One render happens at a time per URL, however many requests arrive together.

The key is the path and the query, because a page reading ?q= renders differently for each one.

Tags

Seconds say when a page may be out of date. A tag says when it is, so something that changed the data can drop it rather than waiting.

${html(s.tagged)}

ctx.revalidateTag drops every held page carrying that tag. It is on the context of a page action or an endpoint, so whatever wrote the change is what says the change happened.

${html(s.drop)} A page that read a cookie, set a header, answered with a Response, or has a status outside 2xx. A shared cache holding any of those hands one visitor's page, or one visitor's Set-Cookie, to the next. It is the same rule the build uses to decide a route can be a file.

The default store is a bounded map in the process. That is right for one server and wrong for several: each holds its own copy, and revalidateTag reaches only one of them. Give cache in the config anything with the same four methods to put the store somewhere they all share.

Caching

Build output is compressed once, and each encoding gets its own ETag.

What Cache-Control
Hashed assets public, max-age=31536000, immutable
Prerendered pages public, max-age=0, must-revalidate
The 500 page no-store, and no ETag

Public files

app/public/ is copied to dist/public and served with byte ranges, so media works.

Error pages

404.html and 500.html are rendered at build time and served as static files. A page that has to render after a request has already failed can fail too, so these are always bytes.

They are written whatever they say, so nothing they render may depend on a request. A layout above them reading a cookie stops the build. ctx.request is null while prerendering, and at no other time, which is how a shared layout can skip the part that needs a visitor.

In production the error is logged and kept out of the page. In dev you get the stack instead.

A page loads a script only if something on it needs one. A page of plain markup and light elements ships none at all.
