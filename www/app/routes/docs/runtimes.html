workerd is the runtime Cloudflare Workers runs on, and it is what is targeted here. Cloudflare is where most people meet it, and wrangler is how you deploy there. Anywhere else that runs workerd runs this.

workerd refuses to compile WebAssembly at runtime. A loader that reaches something built on it fails there and nowhere else. This site hit exactly that. Its syntax highlighter compiles Wasm, so every prerendered page was fine and the one URL that renders live returned 500. A prerendered page never runs its loader in production, which is what hides this until something asks for a fragment.

The Node, Bun and Deno adapters come from the package and only listen. worker.js belongs to the app, and this is all of it.

${html(s.entry)}

The imports stay in the app because a bundler needs a literal path to follow. The wiring behind workerFrom does not, so it lives in the package. It builds the app on the first request, which is when env exists, and reads cookieSecret from env.COOKIE_SECRET when there is one.

An app wanting something else calls createApp from @transclude/core/app and does the wiring itself. That is what this was before there were nine copies of it.

What differs

Each difference from Node is one argument to createApp.

Node workerd
Bytes The filesystem dist/server/assets.js
Hashing node:crypto WebCrypto, so hash is awaited
Compression node:zlib null. The edge does it.
Range requests 206 200
There is no process.env on workerd, so the app is built when the first request comes in and takes its config from env. Reading a secret at import time gives undefined.

Bindings

A KV namespace, a D1 database and a secret all arrive the same way. They are on env, which is the second argument to a worker's fetch.

A loader is not handed that. ctx carries the request, the params and the cookies, and nothing that names one runtime. env names one. The other three fill that slot with something else, so a loader reading it would work in a single place.

worker.js belongs to the app and does get env. Hold it there and import it where a loader needs it.

${html(s.bindings)} ${html(s.hold)} ${html(s.use)}

Env is the interface wrangler types writes. Typing the module is what gives a loader autocomplete on a binding, and the framework could not supply that.

The build runs on Node, where nothing calls hold. A page whose loader reads a binding needs export const prerender = false, or the build runs that loader and throws. The same is true of a page calling ctx.after, for a different reason given below. Holding env in a module is safe, because it is one object for the life of the isolate. Every request served by that isolate gets the same one. Holding a Request this way is not safe, because two visitors would share whichever arrived last.

Nothing calls hold on Node, Bun or Deno, so the throw above is what a loader finds there. An app that runs in more than one place returns its own fallback instead.

Work after the response

ctx.after takes a promise the reader does not have to wait for. A view counted, a webhook sent, a log written.

${html(s.after)}

On workerd this is waitUntil, which is how a worker asks to stay up past the response it just sent. Without it the isolate may stop and take the work with it. Node, Bun and Deno keep running either way, so there it changes nothing about when the work finishes.

It takes the promise, not a function that makes one. Call the work and pass what it returns. A function is refused rather than wrapped, because wrapping one would resolve to the function and run nothing.

Nothing awaits this work, so a rejection would reach the runtime and end the process on Node. It goes to onError instead, with the request that started it. The response is already sent and does not change.

A prerendered page has no response for the work to outlive, so calling it there stops the build. That is the same prerender = false the sample above carries.
