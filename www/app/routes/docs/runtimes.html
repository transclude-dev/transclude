workerd is the runtime that Cloudflare Workers runs on, and this framework targets it. Most people use it on Cloudflare, and you deploy there with wrangler. Any other host that runs workerd also runs this framework.

workerd refuses to compile WebAssembly at runtime. So a loader that uses a library built on WebAssembly fails there and nowhere else. A prerendered page never runs its loader in production. So the failure stays hidden until something asks for a fragment. Syntax highlighting is the most common case. Pick a highlighter that runs on a JavaScript engine.

The Node, Bun and Deno adapters come from the package, and they only listen. On Node, a stop signal drains the server first. The listener closes, the work in progress finishes, and then the process exits. worker.js belongs to the app. This is the whole file:

${html(s.entry)}

The imports stay in the app because a bundler needs a literal path to follow. The wiring behind workerFrom does not need one, so it is in the package. It builds the app on the first request, because env exists only then. It reads cookieSecret from env.COOKIE_SECRET if that is set.

If an app needs something different, it calls createApp from @transclude/core/app and does the wiring itself.

Files on the edge

dist/server/assets.js puts every public file and hashed asset inside the worker. But a worker has a size limit. On Cloudflare, the edge can serve the files instead. Import dist/server/pages.js, which contains only the prerendered pages:

${html(s.edgeEntry)}

Then point the worker's assets at dist/edge:

${html(s.edgeConfig)}

The build writes dist/edge. It contains the public files, the hashed assets, and a _headers file. Cloudflare answers a request for one of those files before the worker runs, so the request costs nothing. The worker answers all other requests. _headers gives each file the headers that the server gives every response. These are nosniff, and also the CSP and the permissions policy when the config sets them. A hashed asset also gets the one-year cache. A _headers file in the public directory is added after the generated rules, and Cloudflare applies both.

Cloudflare's default answers /about with about.html, and redirects /about.html to /about. The Node server does neither for a public file. none makes the two behave the same.

The Node, Bun and Deno servers search up from the working directory for the nearest transclude.config.js. TRANSCLUDE_ROOT starts the search in a different directory. Use it when you start a server outside its project. The build, the dev server and the check also read it.

Minimum versions

Node 22 is the oldest Node version that this runs on. The engines field in both packages says so. CI runs the tests on 22, on Active LTS and on Current. So the minimum version is tested, not only written down.

Bun, Deno and workerd have no minimum version of their own. On every push, CI builds an app and serves it on the current release of each one. So the version that works is the one you can install today. If one of them has a regression, that run catches it.

workerd has no process.env. So the app is built when the first request comes in, and it takes its config from env. If you read a secret at import time, you get undefined.

Bindings

A KV namespace, a D1 database and a secret all come in the same way. They are on env, the second argument to a worker's fetch.

A loader does not get env. ctx contains the request, the params and the cookies, but nothing that belongs to one runtime. env belongs to one runtime. The other three put something different in that place. So a loader that reads it would work in only one place.

worker.js belongs to the app, and it does get env. Store env there, and import it where a loader needs it.

${html(s.bindings)} ${html(s.hold)} ${html(s.use)}

Env is the interface that wrangler types writes. When you type the module, a loader gets autocomplete on each binding. The framework cannot supply that.

The build runs on Node, and nothing calls hold there. A page whose loader reads a binding needs export const prerender = false. Otherwise the build runs that loader, and the loader throws. A page that calls ctx.after needs it too, for a different reason given below. You can safely keep env in a module, because it is one object for the life of the isolate. Every request that the isolate serves gets the same one. Keeping a Request this way is not safe. Two visitors would share whichever request arrived last.

Nothing calls hold on Node, Bun or Deno. So a loader there gets the error that the code above throws. An app that runs in more than one place returns its own fallback instead.

Work after the response

ctx.after takes a promise that the reader does not have to wait for. Examples are a view count, a webhook, or a log entry.

${html(s.after)}

On workerd, this is waitUntil. A worker uses it to stay up after it sends the response. Without it, the isolate may stop and drop the work. Node, Bun and Deno keep running either way. So there, it does not change when the work finishes.

It takes the promise, not a function that makes one. Call the work and pass the value it returns. A function is refused, not wrapped. If it were wrapped, the promise would resolve to the function and nothing would run.

Nothing awaits this work. So on Node, a rejection would reach the runtime and end the process. Instead, it goes to onError with the request that started it. The response is already sent and does not change.

A prerendered page has no response for the work to outlive. So if a prerendered page calls it, the build stops. That is why the sample above has prerender = false.
