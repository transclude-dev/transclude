${html(s.on)}

You need no other setup. Each page gets a policy built from the inline scripts in that page. CSRF protection is on by default.

Escaping

The framework escapes every \${…}. A value that contains markup appears as text. So if a page shows text that a visitor typed, that text cannot run.

${html(s.escaped)} ${html(s.escapedOut)}

html() turns off escaping for one value. With it, you say that the markup is yours. Use it for rendered Markdown that you control, or for output from a library that you trust.

${html(s.trusted)} html() removes nothing from the markup. If you wrap text that a visitor typed, the page runs that visitor's script. The Content-Security-Policy below does not stop it. The script comes from your own origin, in your own document.

The framework parses the HTML before any interpolation runs. So an escaped value cannot open or close an element or a comment. A comment ends where the file ends it. Markup from html() goes where the template put it, and the browser reads it as markup. A </p> in it closes the paragraph around it.

${html(s.parseOrder)}

Scripts and styles cannot contain expressions

Text in a <script> or a <style> goes into the page exactly as written. Escaping it would change what the browser reads. In HTML text, &amp; is one ampersand. In JavaScript, it is five characters. So a value there becomes code. Both of these examples are compile errors.

${html(s.refused)}

No escape can make the first example safe. If a value closes the string around it, the code after the value runs. This is a fact about JavaScript, not about markup.

A <script> at the top level of a page is client code. The build bundles it into a file and does not write it into the page. In it, \${…} is JavaScript's own template syntax.

Data has a safe path. json() writes JSON, and it writes each character that could end the element as \uXXXX. A script can contain one json() call and nothing else. For a style, read the value through a custom property. A custom property is set in an attribute, so it is escaped.

${html(s.jsonOk)}

Hashes, not a nonce

A policy must name each inline script that it allows. There are two ways to do this. A nonce is a random value that the server puts on both the tag and the policy. A hash is a digest of the script's text.

A nonce must be different for each request. The build writes most pages to files, and the server sends those files as bytes. So there is no request to make a nonce for. A hash is set when the page renders, and it stays correct after that. A file needs this.

${html(s.output)} You do not mark your scripts. The framework builds the policy from the document after it renders. So the policy names the scripts that the page really contains. This includes a script that got into the output through html(). The policy blocks scripts that load from other places. It is not a second escape.

Why styles are not hashed

script-src contains hashes, but style-src does not. This looks inconsistent, but it is the only combination that works.

A hash never covers an attribute. The browser checks style="color:red" on an element against style-src. But a hash in style-src applies only to <style> blocks. Adding 'unsafe-inline' too does not help. A directive that contains any hash ignores 'unsafe-inline' completely. So with hashed styles, no element on the page could have a style attribute. But style="view-transition-name: …" is a common thing to write.

The protection matters for scripts, and CSS cannot run code. If your pages have no style attributes at all, put 'hashes' in style-src yourself.

Directives sent as a header

A browser ignores frame-ancestors, report-uri, report-to and sandbox in a <meta> tag. So the server sends them in a response header. None of them names a hash, so that header is the same on every page.

A static host serves the <meta> tag but not the header. If you export the site and need those directives, set them at the host.

Your own directives

Pass directives to replace the defaults. Put 'hashes' in a source list to add the page's own digests there. So you decide which directives get them.

${html(s.custom)}

If a directive has no sources, the framework leaves it out. It does not write the directive empty. An empty list means 'none'. If you say 'none' by accident, the page breaks and is no safer.

Report before you enforce

In report-only mode, the browser reports what the policy would block, but it blocks nothing. So you can test a stricter policy against real traffic first.

${html(s.report)}

The server then sends the whole policy in a Content-Security-Policy-Report-Only header. The header includes the page's hashes. A browser ignores report-only in a <meta> tag, so the framework writes no meta tag.

The server that sends the page sets the header. A host can serve prerendered pages from dist/static and run none of this code. In report-only mode, a page from that host has no policy at all.

The features a page turns off

permissionsPolicy sends a Permissions-Policy header. The header lists the browser features that this app never asks for.

${html(s.permissions)}

true turns off eleven features: cameras, microphones, location, the motion sensors, screen capture, MIDI, USB, payment and topic inference. A document needs none of them to render.

If a page needs one, list it in features. This list replaces the default list. It does not add to it.

${html(s.features)}

An empty array allows nobody, and that includes this page. ['self'] allows this page, but no frame in it.

Turning off the camera takes something away from an app that may need it. So the default is false. A generated project sets it to true. There, the key is in a config file that you own and can read.

The headers that you set

The framework sets the headers that are correct for every app. These are the policy and the features above, and X-Content-Type-Options: nosniff on every response. Two more headers block things that an app may need. The framework cannot find the right values in the config. So you set them in app/server.js.

${html(s.headers)}

Strict-Transport-Security makes every visitor use HTTPS for a year. Referrer-Policy makes a browser default stricter. That default already removes the path from a cross-origin referrer.
