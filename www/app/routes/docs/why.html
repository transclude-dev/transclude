The file is the page

A page here is an .html file. The server renders it, and what arrives is markup a browser already knows how to display.

${html(s.page)}

That file is the whole page. View source shows what you wrote, and the text is on screen before any script runs.

One file, one concern

Server code in an HTML file looks like a mixing of concerns. It is the opposite. A page's data and the markup that reads it are one concern, and they change together. Splitting them into two files splits by technology.

HTML, CSS and JavaScript are three languages. They were never three concerns. A page that loads notes and lists them is one thing to understand, and it reads from top to bottom.

The block costs the visitor nothing. It is compiled into the route and never appears in the page, so none of it reaches the browser.

Not another JavaScript framework

The common shape today is a server that returns JSON and a client that turns it into HTML. That client is a second application. It has its own router, its own copy of the data, and its own idea of what the page currently is. Keeping the two in agreement is most of the work.

Here the server returns the HTML. There is no second copy of the state, because there is no second application. The docs site you are reading ships zero bytes of JavaScript.

Hypermedia

The page is the state of your app, and links and forms are what change it. Follow a link and you have the next state. Nothing on the client had to know what the link meant beforehand.

Roy Fielding named this constraint in the chapter of his dissertation that defines REST: hypermedia as the engine of application state. What the client can do next comes from the representation the server just sent, not from knowledge the client was built with. He wrote about how widely that is missed in REST APIs must be hypertext-driven. An interface that returns JSON and relies on a client that already knows every URL is not doing this.

Ted Nelson coined transclusion in the 1960s: the same piece of writing appearing in more than one document while remaining one piece. That is what this framework is named for, and what fragments are. An element you mark has its own URL, and the same compiled markup serves it inline and alone.

Carson Gross and others have written extensively on building this way, including case studies of applications moved off a JavaScript client.

Does it scale?

The question is usually about the server doing work a client could have done. Three things about this shape answer most of it, and one thing does not.

A render holds nothing. A request comes in, a loader reads it, and bytes go out. Nothing is kept between two requests, so a second machine is a copy rather than a coordination problem. That is the constraint Roy Fielding called statelessness, and it is the reason the web scales at all.

Most pages are not rendered. A page that does not read the request is written to a file at build time. It is compressed once, with a strong ETag for each encoding, so serving it is reading bytes off a shelf. The middle case is a page held for a while. Inside the window the loader does not run. Past it, a stale copy goes out immediately while a fresh one is built behind it.

Nothing grows on the client. A page ships JavaScript only for the elements it renders, and only when one of them has behaviour. The fiftieth feature does not make the first page slower, because there is no bundle for it to land in. This site ships none at all.

A page render costs more than returning JSON. It is usually a small cost against a database query, and it is a real one. Measure before assuming either way.

The honest limit is not throughput, it is the kind of interface. A map, a spreadsheet, a drawing canvas. Anything answering a stream of events in milliseconds wants its state in the browser, and a round trip per event is the wrong shape. Nothing here stops you writing that with the platform, and nothing here helps.

Carson Gross makes the longer version of this argument in Does Hypermedia Scale?. That includes the part nobody has evidence for yet, which is whether it scales with the size of a team.

Foundations

What you learn here is mostly not about this framework. Elements are custom elements. Styles are CSS. A form is a <form>, and it submits without JavaScript. Routes are files in a directory.

That matters for anyone new to the platform. Learning the web and learning a framework are usually two jobs, and the second one expires. Here they are closer to the same job, and the part that lasts is the larger part.

What this does not do

This framework ships nothing that swaps a fragment into a page. htmx, Turbo or a short fetch does that. A fragment has a plain HTTP URL, and that is the whole agreement.

There is no client router, no state store and no data layer for the browser. Those choices are yours. The platform has custom elements, fetch, the History API and view transitions. Every page and fragment here is HTML on a URL, so a client of any size can be built on top.
