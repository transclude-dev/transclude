The file is the page

In transclude, a page is an .html file. The server renders it and sends HTML that the browser can display.

${html(s.page)}

That file is the whole page. View source shows the code you wrote. The text appears on screen before any script runs.

One file, one concern

Server code in an HTML file can look like mixed concerns, but it is not. A page's data and the markup that shows it are one concern. They change together. Two files would split the code by technology, not by concern.

HTML, CSS and JavaScript are three languages, not three concerns. A page that loads notes and lists them is one thing to understand. You read it from top to bottom.

The server block adds nothing to the download. The build compiles it into the route. It never appears in the page, so the browser never gets it.

Not another JavaScript framework

A common design is a server that returns JSON and a client that turns the JSON into HTML. That client is a second application. It has its own router, its own copy of the data, and its own idea of the current page. Most of the work is to keep the two applications in agreement.

In transclude, the server returns the HTML. There is no second application, so there is no second copy of the state. This docs site ships one inline script. It applies the theme.

Hypermedia

The page is the state of your app. Links and forms change that state. When you follow a link, you get the next state. The client does not need to know in advance what the link does.

Roy Fielding named this constraint in the chapter of his dissertation that defines REST: hypermedia as the engine of application state. The last response from the server tells the client what it can do next. The client does not need that knowledge built in. He wrote that many APIs miss this, in REST APIs must be hypertext-driven. An API that returns JSON to a client that already knows every URL does not follow this constraint.

Ted Nelson created the word transclusion in the 1960s. It means one piece of writing that appears in more than one document but stays one piece. This framework takes its name from that idea, and fragments do it. When you mark an element as a fragment, it gets its own URL. The same compiled markup renders it inside the page and on its own.

Carson Gross collects the arguments for this approach in the htmx essays. Several essays are case studies of apps that moved away from a JavaScript client.

Does it scale?

Usually this question asks about the server doing work that a client could do. Three facts about this design answer most of the question. One part stays open.

A render keeps no state. A request comes in, a loader reads it, and the server sends bytes back. The server keeps nothing between two requests. So a second machine is a copy of the first, and the machines need no coordination. Roy Fielding called this constraint statelessness. It is the reason that the web can scale.

Most pages are not rendered for each request. If a page does not read the request, the build writes it to a file. The build compresses it once, with a strong ETag for each encoding. So the server only reads stored bytes to serve it. The middle case is a page that the server caches for a set time. During that time, the loader does not run. After that time, the server sends the stale copy at once and builds a fresh one in the background.

The client code does not grow. A page ships JavaScript only for the elements it renders, and only when one of them has behavior. Your fiftieth feature does not make the first page slower, because there is no shared bundle. This site's elements ship no JavaScript.

A page render costs more than returning JSON. Compared to a database query, the cost is usually small. But it is a real cost, so measure it before you decide.

The real limit is the kind of interface, not throughput. Examples are a map, a spreadsheet or a drawing canvas. Such an interface must respond to a stream of events within milliseconds. It needs its state in the browser, because one round trip per event is the wrong design. You can build it with the platform, but this framework does not help.

Carson Gross gives a longer version of this argument in Does Hypermedia Scale?. He also covers one open question: does it scale with the size of a team? Nobody has evidence for that yet.

Foundations

Most of what you learn here is not specific to this framework. Elements are custom elements. Styles are CSS. A form is a <form>, and it submits without JavaScript. Routes are files in a directory.

This helps people who are new to the web platform. Usually, learning the web and learning a framework are two jobs. Framework knowledge goes out of date. Here the two jobs are almost the same, and most of what you learn stays useful.

What this does not do

This framework has no code that swaps a fragment into a page. Use htmx, Turbo or a short fetch for that. A fragment has a plain HTTP URL, and that URL is the whole contract.

There is no client router, no state store and no data layer for the browser. You choose those. The platform gives you custom elements, fetch, the History API and view transitions. Every page and fragment is HTML at a URL. So you can build a client of any size on top.
