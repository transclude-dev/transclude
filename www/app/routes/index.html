#transclude

An HTML-first server-side web framework.

HTML is the product.

A page is one .html file: the markup, and the server code that loads its data. The directory tree is the route table. Any part of a page can be asked for on a URL of its own, and the server sends HTML either way.

Any element can be a URL

A page is one .html file. Put fragment on an element inside it, and that element answers on a URL of its own.

${html(s.page)}

One word, and the page answers two requests.

GET /notes the whole document
GET /notes?fragment=list the <ul> and nothing else

Both come from the same compiled markup, so the page and the piece cannot drift apart. That is the whole agreement: a fragment is a resource with a plain HTTP URL.

Nothing here swaps one into a page. htmx, Turbo or a few lines of fetch does that, and the choice stays yours.

The server can put that element in a second place instead. <transclude src="#list"> renders it somewhere else on the page, and src="/notes#list" reaches into another route. Showing the same content in more than one place is what the word transclusion means. It is where the name of this framework comes from. Includes covers it.

You are reading a fragment.

This box is part of the page you loaded, and it is also its own URL. /?fragment=demo returns the markup of this box and nothing else. No <head>, no layout, no second template. Open it and compare.

One file is one route

app/routes/notes.html responds to /notes. The <script server> block above is the loader: it runs on the server and returns the data the markup reads. export const POST answers the form. No client JavaScript is involved.

The loader and the markup that reads it change together, so they are one file to open and one file to review. Splitting them would split by technology rather than by concern. The block is compiled into the route and never appears in the page, so none of it reaches the browser.

Three languages, and one loop

You write HTML, CSS and JavaScript. The file you edit is the page that ships, and view source shows what you wrote.

There is no client application, so nothing holds a second copy of the state and nothing has to run before the text appears.

Save the file and hot reload does the refresh. That is the loop: Command-R programming, without the Command-R.

Why this exists goes further. The server returns the HTML, and links and forms are what change the state. That idea is older than the problem it solves.

No JavaScript by default

A page ships JavaScript only for the custom elements it renders, and only when one of them has behavior. This site ships none.

Four runtimes, one app

Node, Bun, Deno and workerd, the runtime behind Cloudflare Workers. The core imports nothing from node: and touches no Node-only global, both of which are tested. This site runs on it.

Types without TypeScript

npm run check reads the shapes your loaders already return. A misspelled field in a template is an error rather than a blank space on the page. No annotations, and these pages are checked on every commit.

Prerendered where it can be

A page that does not read the request is written to a file, compressed once at rest, with a strong ETag per encoding. Everything else is rendered by the server, on the same routes. This site is both.

Start a project

Four commands and you have a site running on localhost:1960. It writes a layout, two pages, a 404 and a stylesheet, and nothing you have to delete. --template blank writes one page instead.
