#transclude

An HTML-first server-side web framework.

HTML is the product.

A page is an .html file. The directory tree is the route table. The server renders the page and sends markup a browser already knows how to display, so nothing has to run in the browser for the page to be correct.

Get started Documentation GitHub

One file is one route

app/routes/notes.html answers /notes. The <script server> block is the loader: it runs on the server and returns the data the markup reads. export const POST answers the form. No client JavaScript is involved.

${html(s.page)}

The loader and the markup that reads it change together, so they are one file to open and one file to review. Splitting them would split by technology rather than by concern. The block is compiled into the route and never appears in the page, so none of it reaches the browser.

Any region can be a URL

Add fragment to an element and it gets a URL of its own.

${html(s.region)}

That one word makes the page answer two requests.

GET /notes the whole document
GET /notes?fragment=list the <ul> and nothing else

Both come from the same compiled markup, so the page and the piece cannot drift apart. That is the whole agreement: a region is a resource with a plain HTTP URL.

Nothing here swaps one into a page. htmx, Turbo or a few lines of fetch does that, and this framework ships none of them.

The server can put a region in a second place instead. <transclude src="#list"> renders this one somewhere else on the page, and src="/notes#list" reaches into another route. Showing the same content in more than one place is what the word transclusion means, and it is where the name comes from. Includes covers it.

You are reading a fragment.

This box is part of the page you loaded, and it is also its own URL. /?fragment=demo returns the markup of this box and nothing else. No <head>, no layout, no second template. Open it and compare.

Three languages, and one loop

You write HTML, CSS and JavaScript. The file you edit is the page that ships, and view source shows what you wrote. There is no component tree to reconcile, no hydration step, and no build output the browser has to run before the text appears.

Nothing on the client holds a second copy of the state, because there is no client application. So there is nothing that can disagree with the server, nothing to rehydrate, and when a page is wrong there is one place it can be wrong.

Save the file and refresh. That is the loop, and it is the whole loop. Hot reload is here and it is a convenience: the page is correct without it, which is the point.

Why this exists goes further: the server returns the HTML, links and forms are what change the state, and that idea is older than the problem it solves.

No JavaScript by default

A page ships JavaScript only for the custom elements it renders, and only when one of them has behavior. This site ships none.

Four runtimes, one app

Node, Bun, Deno and workerd, the runtime behind Cloudflare Workers. The core imports nothing from node: and touches no Node-only global, both of which are tested. This site runs on it.

Types without TypeScript

A misspelled field, an unknown prop and a wrong-typed one are caught from the shapes your loaders already return.

Prerendered where it can be

A page that does not read the request is written to a file, compressed once at rest, with a strong ETag per encoding. Everything else is rendered by the server, on the same routes. This site is both.

Start a project

Four commands and you have a site running on localhost:1960. It writes a layout, two pages, a 404 and a stylesheet, and nothing you have to delete. --template blank writes one page instead.

${html(s.start)}
