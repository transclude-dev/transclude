An HTML-first server-side web framework.

HTML is the product.

A page is one .html file. It contains the markup and the server code that loads its data. The directory tree is the route table. You can request any part of a page at its own URL. The server sends HTML in both cases.

Any element can have its own URL

A page is one .html file. Add fragment to an element in the page, and that element gets its own URL.

${html(s.page)}

One attribute gives the page two URLs.

GET /notes the whole document
GET /notes?fragment=list the <ul> and nothing else

Both responses come from the same compiled markup, so the page and the fragment always match. That is the whole contract: a fragment is a resource with a plain HTTP URL.

transclude does not swap a fragment into a page. Use htmx, Turbo or a few lines of fetch for that. You choose which one.

Or the server can put that element in a second place. <transclude src="#list"> renders it in another part of the page. src="/notes#list" gets it from another route. The word transclusion means showing the same content in more than one place. This framework takes its name from that word. Includes explains how it works.

You are reading a fragment.

This box is part of the page you loaded. It also has its own URL. /?fragment=demo returns only the markup of this box. There is no <head>, no layout and no second template. Open it and compare.

One file is one route

app/routes/notes.html responds to /notes. The <script server> block above is the loader. It runs on the server and returns the data for the markup. export const POST handles the form. No client JavaScript runs.

The loader and the markup change together, so you open and review one file. Two files would split the code by technology, not by concern. The build compiles the block into the route. It never appears in the page, so the browser never gets it.

Three languages, and one loop

You write HTML, CSS and JavaScript. The file you edit is the page that ships. View source shows the code you wrote.

There is no client application. So no second copy of the state exists, and no code has to run before the text appears.

Save the file, and hot reload refreshes the page. You get the edit and reload loop, but you do not press Command-R.

Why this exists explains more. The server returns the HTML, and links and forms change the state. This idea is older than the problem it solves.

No JavaScript by default

A page ships JavaScript only for the custom elements it renders, and only when one of them has behavior. This site ships none.

Four runtimes, one app

Node, Bun, Deno and workerd, the runtime behind Cloudflare Workers. The core imports nothing from node: and uses no Node-only global. Tests check both. This site runs on workerd.

Types without TypeScript

npm run check reads the shape of the data your loaders return. A misspelled field in a template is an error, not a blank space on the page. You write no annotations. These pages get a check on every commit.

Prerendered when possible

If a page does not read the request, the build writes it to a file. The build compresses the file once and gives each encoding a strong ETag. The server renders all other pages, on the same routes. This site uses both.

Start a project

Run four commands, and you have a site on localhost:1960. The project has a layout, two pages, a 404 page and a stylesheet. You do not have to delete any of it. --template blank writes one page instead.
